Show me how you would implement your solution in code.

Four functions: the constants from θ and χ, the travelling coordinate ξ, the auxiliary function δ, and U = B₁δ. Everything in complex arithmetic, and plot the modulus.

The structure, which you should be able to sketch from memory:

constants(theta, chi) -> l, m, omega, B1, zeta xi_of(x, y, t, ...) -> Eq. (12) delta(xi, chi, P,S,R) -> Eq. (10) if chi<0 else Eq. (11) U(...) -> B1 * delta(xi_of(...))

The one design decision worth explaining unprompted: use np.emath.sqrt, not np.sqrt. The radicands are genuinely negative at these parameters — B₁ ≈ 0.633i — so plain np.sqrt returns nan and silently destroys the result. np.emath.sqrt promotes to complex.

It is all running on page 11. Being able to open it and run it is worth more than describing it.

Y02

How did you find the error in your constants?

By writing the solution as code and substituting it back into the equation — the check the report never contained.

The method is worth describing because it generalises: compute u″ by central differences, form the residual ½u″(l² − ω²) + ζu + u³, and take the maximum modulus over a sample of ξ, normalised by the size of u³ so the number is dimensionless. If the solution is right the residual sits at the truncation error of the difference formula, around 10−6 for h = 10−5. It came out at order one, which meant something was wrong with the constants rather than with the arithmetic.

Then bisect: δ satisfied its own ODE to 10−8, so Eqs. (10) and (11) were fine. That left ω and B₁, and the condition B₁² = ω² − l² identified which of the two was inconsistent.

This is a debugging story with a clean method and a definite outcome. It is one of the best things you can talk about.

Y03

Why NumPy rather than loops?

Because the loop runs in the Python interpreter and the array operation runs in compiled C over contiguous memory — typically one to two orders of magnitude faster, and the code is shorter.

The deeper reason, which matters for PDE work: array expressions map directly onto the mathematics. np.abs(U(X, 1.0, T)) over a meshgrid is the surface. There is no index bookkeeping to get wrong.

Know the cost too: vectorising allocates temporaries. For a large grid a chain of array expressions can use several times the memory of the result, and that is when you reach for in-place operations or numexpr.

Y04

How would you plot a 3D surface that goes to infinity?

Clip it and say so in the caption — which is what Maple did in my Figure 1, stopping the axis at 9 against a plateau of 1.4.

The options: clip with np.clip, plot on a log scale, or mask the neighbourhood of the pole with nan so matplotlib leaves a hole. Masking is the most honest, because it shows visually where the solution ceases to exist rather than drawing a flat plateau that looks like real data.

The presentational point is the important one: a clipped axis with no note is misleading. This is precisely the criticism available against Figure 1 as published, and naming it before the panel does is worth doing.

Scientific computing

Y05

Write a split-step Fourier solver for the NLS.

Half a linear step in Fourier space, a full nonlinear step in physical space, half a linear step again — Strang splitting, second-order accurate.

k = 2*np.pi*np.fft.fftfreq(N, d=L/N) Lh = np.exp(-0.5j * k**2 * (dt/2)) # half linear step for n in range(steps): U = np.fft.ifft(Lh * np.fft.fft(U)) # half linear U = U * np.exp(1j * np.abs(U)**2 * dt) # full nonlinear, exact U = np.fft.ifft(Lh * np.fft.fft(U)) # half linear

Two things to be able to explain. Why the nonlinear step is exact: over that substep the equation is iUt = −|U|²U, and |U|² does not change, so the update is a pure phase rotation with no error at all. Why Fourier: the linear operator is diagonal in Fourier space, so the linear step is exact too — all the error comes from the splitting, not from either piece.

Caveats worth volunteering: periodic boundary conditions are implied, and you need enough resolution that the highest Fourier mode is not excited, or you get aliasing.

Y06

How do you verify a solver converges at the right rate?

Halve the step, measure the error against an exact solution, and check the ratio. Second order means the error should fall by four; a log–log plot of error against step size should have slope 2.

If no exact solution is available, use a much finer run as the reference, or use the method of manufactured solutions: pick the answer you want, substitute it into the PDE, and add whatever source term makes it exact.

Then connect it back: "my project's exact solutions are usable as the reference in the first version of this test, which is the least common of the three ingredients."

Y07

What is catastrophic cancellation, and where might it bite here?

Subtracting two nearly equal floating-point numbers destroys significant digits. In these solutions it lurks in Δ = 4χ²l⁴ − 12χl⁴ + … , where large terms of opposite sign can cancel down to something small.

The classic illustration is the quadratic formula: when b² ≫ 4ac, one of the roots computes as a difference of nearly equal quantities and loses precision; the fix is to compute the well-conditioned root and get the other from the product of the roots.

The relevant practical answer here: my Δ evaluates to 16.2 at θ = 60°, χ = −5, from terms of size up to 30, so there is no problem at these parameters — but it would be worth checking near angles where Δ approaches zero, since B₁ and ω both depend on √Δ and the solution degenerates there.

Y08

Why is float64 the default in scientific computing?

About 16 significant decimal digits, with machine epsilon near 2.2 × 10⁻¹⁶. That leaves enough headroom for error to accumulate over millions of operations without contaminating the result.

float32 gives about 7 digits, which is often not enough once a time-stepping scheme has run for 10⁶ steps and rounding errors have accumulated. It is used where memory bandwidth dominates — large-scale CFD, and machine learning, where the tolerance for noise is much higher.

Worth knowing the standard traps: 0.1 + 0.2 != 0.3, never compare floats with ==, and summation error grows with the number of terms unless you use pairwise or Kahan summation — which NumPy's sum already does pairwise.

Engineering practice

Y09

How does your industry experience help in research computing?

Reproducibility and testing. Most research code is written once by one person and never tested; six years of professional practice means version control, tests, and code someone else can actually run.

Be concrete rather than generic:

  • Version control — every result traceable to the commit that produced it.
  • Testing — a solver should have a convergence test in CI, not a note in a notebook saying it worked once.
  • Databases and data handling — parameter sweeps generate a lot of runs, and organising them is an ordinary engineering problem I have solved many times.
  • Performance — profiling before optimising, and knowing that the answer is usually an algorithm rather than a micro-optimisation.

The honest caveat, which makes the rest credible: web and API work is not numerical work. What transfers is discipline and tooling, not domain knowledge.

Y10

How would you test numerical code, given the answer is never exactly right?

Test properties rather than values: convergence rates, conserved quantities, symmetries, and known exact cases within a tolerance.

  • Exact cases. A linear problem, a steady state, or an analytical solution — assert agreement to a stated tolerance.
  • Convergence order. Refine and assert the observed order is within a tolerance of the theoretical one. This catches whole classes of subtle bugs that a single-resolution test misses.
  • Invariants. Mass and energy for the NLS. A drift means a bug, and it is checkable every step.
  • Symmetry. Translate the initial data and confirm the result translates with it.
  • Regression. Store a known-good output and compare against it within tolerance so you notice unintended change.

The convergence-order test is the one that marks out someone who has actually done this. Lead with it.

Y12

SymPy or hand algebra?

Both, and always the second as a check on the first — which is exactly the lesson of the ω error.

A CAS does not make mistakes in the algebra; the mistakes happen at the boundaries — entering the problem, choosing among the roots it returns, and copying the answer out. All three are human steps, and the last one is where my error occurred.

The practical discipline that follows: whatever the CAS returns, substitute it back numerically. It takes minutes and it catches the entire class of transcription error.
